# XAnalyze (`ai-content-scanner`) - правила репозиторія

Глобальний протокол - `~/.claude/CLAUDE.md` і канон сховища. **Тут лише те, що з них не
виводиться:** гілки, команди, архітектурні інваріанти цього коду. Протокол Second Brain у цьому
файлі не переказується: переказ дрейфує від канону, і саме так застарів `xformat-backend/CLAUDE.md`.

## Прив'язка до сховища

- Папка проєкту: `Projects/XAnalyze/` - канбан `STATE.md`, етапи `Roadmap.md`, `Problems.md`,
  `Planning/`, `Архів/`, `TODO.md`, `manual-todo.md`, `RESEARCH/`, `Devs/`, `Design/`.
- **Плани живуть у сховищі, не в репозиторії.** Тека `Planning/` у корені репо була помилкою
  (виправлено 2026-08-25): такий план невидимий для канбану і `vault-lint`, тож задача тихо
  отримує другого власника. Не створюй її знову.
- Файла стану в репо немає, на відміну від `xformat-backend`. Стан живе в канбані сховища.
- `Devs/` - жива документація коду, дрейфує від коду: перед довірою застосуй `devs-audit`.

## Збірка бандлів

Заморожені бінарники (PyInstaller) містять `config.py` на момент збірки і **не оновлюються
автоматично**. Застарілий бінарник бреше про свою версію. Бінарник попереджає про розбіжність,
якщо поруч лежить `.build_version`, але краще не допускати:

```bash
make version           # поточна версія з config.py
make check-cli         # чи зібраний CLI відповідає коду?
make check-app         # чи зібраний App відповідає коду?
make rebuild-cli       # перебудувати CLI-бандл
make rebuild-app       # перебудувати GUI-бандл
make rebuild-all       # обидва
```

Під час збірки `Makefile` автоматично записує `.build_version` поруч із бінарником.
**Піднімай версію в `config.py` до збірки**, інакше зібране бреше про себе одразу.

## Архітектурні інваріанти

Повний опис - `Projects/XAnalyze/Devs/ARCHITECTURE.md`. Те, що ламається найчастіше:

- **Один факт має одного власника.** Найдорожчий клас дефектів тут, і **жоден із них не падав**:
  вікно тримало копії стану, якого ніхто не заповнював, через що аудит теки слав
  `https:///Users/...` у краулер і звітував порожній результат як чистий. Стан прогону читається
  через властивості **без сеттера**, тому спроба записати стару копію падає, а не розходиться.
- **Три точки входу, одне ядро.** `main.py` тонкий навмисно, `cli.py` не імпортує GUI-модулі на
  рівні файлу, `tui/` - обгортка над CLI, `app_entry.py` лише для зібраного бандла.
- **Що куди не має знати:** `detectors/*` не імпортують веб- чи репо-специфічного;
  `ui/tokens.py` парсить дизайн-систему, `ui/theme.py` малює нею; `report/*` не імпортує
  `i18n.translations` - у звіту власний словник у `report/template.py`.

## Версія

`APP_VERSION` у `config.py` є єдиним місцем, де записана версія: бандли беруть її звідти, тож
достатньо однієї правки. Крок обирається за тим, що зайшло **з часу попереднього підняття**, а не
за кожним комітом окремо:

| Що зайшло | Крок | Приклад |
|---|---|---|
| Нова функціональність (`feat`) | середнє число | `0.11.0` -> `0.12.0` |
| Лише виправлення (`fix`), рефакторинг, документація | останнє число | `0.12.0` -> `0.12.1` |
| Реліз або кардинальна зміна | перше число | `0.12.1` -> `1.0.0` |

Є і фічі, і фікси - виграє більший крок: середнє число піднімається один раз, фікси в нього
входять. Піднімай версію **до** збірки бандлів, інакше зібране бреше про себе одразу після збірки.

## README

Додана або змінена функціональність описується в README **тією ж роботою**, що її вводить, і
**в усіх трьох мовах**: `README.md`, `README_ua.md`, `README_it.md`. Правка лише англійського
робить два інші файли ще старішими за код.

Мінімум на фічу: рядок у `Можливості` / `Features`, і розділ, якщо поведінка не пояснюється одним
рядком. Змінилися вимоги до середовища або межі того, що вміє **зібраний** бандл - це теж README,
а не лише код: людина читає README до того, як щось запустить.

Чому це правило коштувало окремої задачі: секція `Features` не знала про цілий прохід
`audit/media.py` і `audit/repo_facts.py`, а `Requirements` казав `Python 3.9+` уже після переходу
на 3.14, тобто README не просто мовчав, а вів у `SyntaxError`.
